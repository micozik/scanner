## URL / link handling

- [stated] Always put ALL requested report URLs in one single code block — never split across multiple blocks
- [stated] Use jsdelivr mirror URLs: `https://cdn.jsdelivr.net/gh/micozik/scanner@main/reports/<file>` — this is the only form that reliably returns the current report
- [stated] The old `?v=` cache-busting convention on raw.githubusercontent.com is dead — query parameters get stripped, so every `?v=` variant hits the same stale cache; `github.com/blob/` URLs are stale too
- [stated] ★★ GitHub Pages is now the fixed daily form ★★ — `https://micozik.github.io/scanner/reports/<file>`; no SHA, no purge, no parameters, and it returned a fresher report than jsdelivr did. Same three URLs every day
- [stated] ⚠️ Even the fixed Pages URL goes stale for Claude — Claude's own fetcher caches by URL, so `latest.txt` returns the first copy it ever fetched. Fix in place: patch18b writes a run-numbered copy `reports/r<GITHUB_RUN_NUMBER>.txt` each run, so the daily link is `https://micozik.github.io/scanner/reports/r<运行号>.txt` (run number = the `#NNN` on the Actions home page; the Actions log prints the full link at the end)
- [stated] Commit-SHA form `https://cdn.jsdelivr.net/gh/micozik/scanner@<sha>/reports/<file>` (7-char SHA from the repo home page) is the fallback if Pages ever goes stale — every commit is a new path so no cache can be hit
- [stated] `@main` caches ~12h; the purge URLs (`https://purge.jsdelivr.net/gh/micozik/scanner@main/reports/<file>`) only work when Zikye opens them in his own browser — Claude's own purge fetch returns a cached `status: finished` response and does nothing
- [stated] If a fetch fails: generate corrected URLs immediately; wait for Zikye to re-send before analyzing — never analyze stale or missing data
- [stated] ★ Zikye (2026-09-21): "想办法抓最新，以后不要我提" — when he says he ran a scan, Claude fetches `https://micozik.github.io/scanner/reports/latest.txt` itself first (the fetcher cache expired after a few days and it returned the current report); only ask him for the `r<运行号>` link if the timestamp is stale

## Code patching workflow

- [stated] Deliver changes as small numbered patch files (patch.py, patch12.py, etc.) — never regenerate the full 376KB main file
- [stated] scan.yml automatically runs all patch*.py files in sequence
- [stated] Mobile download renames underscores to spaces — yml files must handle both naming conventions
- [stated] GitHub Actions main workflow timeout raised from 22 to 90 minutes (the 22-min cap was killing runs before reports were written)
- [stated] ⚠️ scan.yml sets env vars on the 运行扫描 step (e.g. `HARD_LIMIT: '1020'`) — env vars override code defaults, so a patch that edits a constant in scanner_cloud.py silently does nothing until the matching line in scan.yml is changed too; check scan.yml env before patching any constant
